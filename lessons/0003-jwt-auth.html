第 3 课 · JWT 鉴权

Phase 0 巩固 CEX · 把「已登录用户」挂进请求上下文，为充值 / 提现的身份校验打底

本课目标：给服务加一层鉴权中间件——客户端登录拿到 token，之后每个请求在 Authorization 头带上它，中间件验签通过就把 user_id 注入请求上下文，handler 直接取用。本课不写业务，只立「身份从哪来」这跟柱子。

① 流程图（本课点亮「鉴权」横切层）

② 整体思考（先想清楚再敲）

JWT 是什么

JWT（JSON Web Token）是一串 aaa.bbb.ccc 三段 base64：header.claims.signature。服务端用密钥对前两段签名，客户端拿着整串；服务端收到后验签，签名对就信任里面的内容。它不需要在服务端存 session——这就是「无状态鉴权」，对横向扩容的交易所后端很关键。

前端类比JWT 对应物说明
路由守卫 router.beforeEachGin 中间件 AuthRequired()每个请求前的统一关卡
登录后存 localStorage 的 token客户端持有的 JWT都靠客户端携带，服务端不存

守卫失败 next('/login')c.AbortWithStatusJSON(401, ...)拦截并回 401

落点：为什么进 internal/server

第 2 课我们约定：internal/server 是「引擎 + 全局中间件」层，不装具体业务 handler。JWT 恰恰是横切所有模块的基础设施（账户、充值、提现都要验身份），所以它是 internal/server 的天然住户，和账户模块各司其职。

关键边界（记牢）：中间件只做两件事 —— ① 验签名、② 把 user_id 注入 ctx。不做任何业务判断。至于「这个 user 能不能提现 100 万」那种规则，是风控层（C 阶段）的事，不是鉴权层。

本课怎么和账户模块接上

第 2 课账户接口是用路径里的 account_id 定位的。鉴权进来后，正确做法是：token 解出 user_id → 由 user_id 找到 account_id。现在内存里 Account 已经带了 UserID 字段，所以「user→account 映射」天然成立。本课只先打通中间件 + ctx 注入，handler 里演示怎么取 user_id；要不要把账户接口全改成「凭 user_id 定位」属于后续重构，不转移本课重心。

Step 3 — internal/server/middleware.go：AuthRequired 中间件

  • 目标：返回 gin.HandlerFunc。从 Authorization 头取 Bearer <token>，验签，失败 401 并中断；成功把 user_id 注入 ctx 再放行。
  • 骨架 + 关键行：
func AuthRequired() gin.HandlerFunc {
    return func(c *gin.Context) {
        // 1) h := c.GetHeader("Authorization")，去掉 "Bearer " 前缀
        // 2) uid, err := ParseToken(token)；err != nil → c.AbortWithStatusJSON(401, ...) 并 return
        // 3) c.Set("user_id", uid)   // 注入请求上下文
        // 4) c.Next()                // 放行给下一个 handler
    }
}
坑：头可能是空、或没有 Bearer 前缀、或 token 过期。三种都要在 err != nil 分支统一回 401，别让 panic 漏出去。

Step 4 — cmd/server/main.go：挂中间件 + 临时 /login

  • 目标：用路由组把受保护接口圈起来；加一个临时 POST /login（mock：收 user_id 直接发 token，接真实用户系统前先用它跑通）。
  • 关键示意（片段，不是整文件）：
r := gin.Default()

// 临时登录：拿到 token 用，后面接真实用户库
r.POST("/login", func(c *gin.Context) {
    var req struct{ UserID string `json:"user_id"` }
    c.ShouldBindJSON(&req)
    token, _ := server.GenerateToken(req.UserID)
    c.JSON(200, gin.H{"token": token})
})

// 受保护组：下面所有路由都要过鉴权
auth := r.Group("/api")
auth.Use(server.AuthRequired())
account.RegisterRoutes(auth, accountSvc)  // 第2课的方法，签名不变
注意：account.RegisterRoutes 签名不用改，因为鉴权发生在它之前（中间件层），handler 内部才去 c.Get。这正是分层的好处——加鉴权不必动每个 handler 的注册。

Step 5 — 在 handler 里取身份

账户 handler（或任何模块）想拿当前用户，不再靠请求体传，而是：

uid, _ := c.Get("user_id")          // 中间件注入的
// 之后用 uid 做定位 / 写流水 / 风控校验

第 2 课你写的 GetBalance / Deposit 现在可以顺势改成「凭 uid 找账户」——但本课只要求你理解并能取出 uid，要不要全量重构账户接口交给你决定，不强制。

④ 跑通校验

# 1) 登录拿 token
TOKEN=$(curl -s -X POST localhost:8080/login -H 'Content-Type: application/json' \
  -d '{"user_id":"u1"}' | python3 -c "import sys,json;print(json.load(sys.stdin)['token'])")

# 2) 带 token 访问受保护接口 → 期望 200
curl -H "Authorization: Bearer $TOKEN" localhost:8080/api/accounts/u1/balance

# 3) 不带 token → 期望 401
curl localhost:8080/api/accounts/u1/balance
校验标准：第 2 步返回余额 JSON；第 3 步返回 401 且被中间件拦截（不会打到 handler）。两者都满足，本课通过。

⑤ 生产 reality（⚠️ 可选扩展，不转移主线）

主题生产中真实做法你现在
密钥管理进 KMS / Secret Manager / env，绝不硬编码进代码或进 git常量占位，记住要换
算法内部服务用 HS256 够；对外/多方可换 RS256（非对称，公钥验签）HS256
续期access token 短命 + refresh token 换发单 token 2h
注销 / 风控token 黑名单（Redis）、异常登录直接让中间件拒掉无
防重放jti + Redis 去重，或 nonce 时间戳无
传输必须 HTTPS；Bearer 头别落日志本地 http
安全红线：① 别用 SigningMethodNone（任何人都可伪造）；② HS256 的密钥要够长够随机；③ 验签时务必显式校验算法，防止「算法混淆」攻击（golang-jwt v5 默认已校验，但要知道这回事）。这些留到 C 阶段深讲。
