第 4 课 · 撮合引擎入门

Phase 0 巩固 CEX · 交易所的心脏：价格交叉就成交，没成交的挂进订单簿

本课目标：理解并跑通一个最小撮合引擎——接收一笔订单，跟对手盘逐笔撮合，能成交的生成 Trade、不能成交的挂进订单簿。本课只做撮合本身，不碰「用户有没有钱」（那是提交订单之前、风控层的事，呼应你之前 review 的 book.go 边界）。

撮合引擎到底在干嘛

一句话：把「想买的人」和「想卖的人」按价格撮到一起。它维护两个队列——买盘 bids（大家挂的买单）和 卖盘 asks（大家挂的卖单）。新订单进来时：

  • 买单来价格 P：去卖盘找「价格 ≤ P」的卖单，从最便宜的开始逐笔吃（价格优先）。
  • 卖单来价格 P：去买盘找「价格 ≥ P」的买单，从最贵（出价最高）的开始逐笔吃。
  • 吃的过程中每成交一笔，生成一个 Trade（成交记录）。
  • 主动单吃不完的部分，就挂进自己的盘，等后面的人来撮。
前端类比撮合引擎对应说明
事件队列 / 消息总线订单流（不断进来的 order）都是「来一个处理一个」
数组按字段 sort 后取极值bids 降序 / asks 升序价格优先 = 排序后从头取
reducer 产生新状态 + action 日志Book 状态变化 + Trade 流水成交可回放（类似 ledger）
纯函数（输入→输出，不改外部）撮合核心 Submit理想情况下可单测、可回放

落点：为什么进 internal/match

按第 2 课定的「模块式」约定，每个业务域一个包、自带 {model,service/handler} 并暴露 RegisterRoutes。撮合是独立业务域，所以住 internal/match，和账户、后续充值/提现平级。它只依赖自己的内存订单簿，不反向依赖账户——保持「引擎不知道钱」的干净边界（你之前 review book.go 时纠结的正是这点）。

关键边界（记牢，呼应 book.go）：撮合引擎只回答两个问题 —— ① 这笔单能不能和现有盘口成交？② 成交了多少、价多少？ 它不查余额、不扣钱、不拒「买不起」的订单。判断「这个用户是否有权下这笔单」是提交订单之前风控层（C 阶段）的职责。把资金判断塞进撮合，就是越界。

本课先做什么、不做什么

  • 做：限价单（你挂一个明确价格）+ 价格优先撮合 + 生成 Trade + 挂单。
  • 不做（留 C 阶段或后续）：市价单、冰山单、IOC/FOK 等高级单、盘口持久化、成交后真正扣减账户余额（那要接账户服务，是闭环的一部分，本课先让引擎独立跑通）。

Step 1 — internal/match/model.go：订单与成交的结构

  • 目标：定义 Order（一笔挂单/委托）和 Trade（一次成交）。价格、数量都用 decimal.Decimal（和账户模块一致，绝不用 float）。
  • 骨架（只给字段，方法体/常量你来补）：
package match

import (
    "time"
    "github.com/shopspring/decimal"
)

type Side string

const (
    SideBuy  Side = "buy"
    SideSell Side = "sell"
)

type Order struct {
    ID        string
    UserID    string
    Side      Side
    Price     decimal.Decimal // 限价单的挂单价格
    Amount    decimal.Decimal // 剩余未成交数量（撮合中会被扣减）
    CreatedAt time.Time
}

type Trade struct {
    ID        string
    BuyerID   string
    SellerID  string
    Price     decimal.Decimal // 成交价（取挂单方价格，price-time 优先）
    Amount    decimal.Decimal // 成交量
    TakerSide Side            // 主动方方向，记录谁发动了这笔成交
}
填空提示：Amount 初始等于用户下单量；撮合时逐步扣减，扣到 0 表示完全成交。状态字段（挂单中/部分成交/完全成交）本课可省略，靠 Amount 是否为零判断即可。

Step 2 — internal/match/book.go：撮合核心

  • 目标：Book 持有 bids / asks 两个切片 + 一把锁（并发下单数）；Submit(o *Order) []Trade 是心脏，返回本次产生的成交；外加一个只读快照 Snapshot() 供外部（handler）查看盘口——字段是不导出的，且读也要持锁。
  • 骨架 + 关键行（Submit 方法体你来填，这是本课重点；Snapshot 完整给出，照抄即可）：
type Book struct {
    mu    sync.Mutex
    bids  []*Order // 买盘：价格降序（出价高的在前）
    asks  []*Order // 卖盘：价格升序（要价低的在前）
}

func New() *Book { return &Book{} }

// Snapshot 只读快照：持锁拷贝一份盘口交出去（handler 的 GET /orderbook 用它）
// 为什么不让外部直接读 b.bids / b.asks：① 封装（字段故意不导出）；② 读也要持锁；③ 别把内部切片头泄漏出去
func (b *Book) Snapshot() (bids, asks []*Order) {
    b.mu.Lock()
    defer b.mu.Unlock()
    return slices.Clone(b.bids), slices.Clone(b.asks) // 需要 import "slices"
}

// Submit 接收一笔新订单，内部撮合，返回本次产生的成交列表
func (b *Book) Submit(o *Order) []Trade {
    b.mu.Lock()
    defer b.mu.Unlock()

    var trades []Trade
    // 1) 按方向取对手盘：buy 找 asks，sell 找 bids
    // 2) 循环：只要对手盘非空 & 价格交叉，就撮一笔
    //    - 价格交叉条件：buy → 对手 asks[0].Price <= o.Price
    //                     sell → 对手 bids[0].Price >= o.Price
    // 3) 每笔：tradePrice = 挂单方价格（对手盘头部那个）
    //          tradeAmt   = min(o.Amount, 对手.Amount)
    //          双方 Amount 减去 tradeAmt；记录 Trade 到 trades
    //          对手 Amount 归零 → 从盘口移除（切片删除头部）
    // 4) o.Amount 归零 → 跳出循环（主动单吃完）
    // 5) 循环结束，o 还有剩余 → 挂入本方盘（bids 或 asks），保持排序
    // 6) return trades
}
坑（新手必踩）：① 切片删除头部用 asks = asks[1:]，注意这会改变底层数组，锁内操作没问题但别在锁外共享；② 价格比较用 decimal 的方法（a.Cmp(b) <= 0 表示 a≤b），别用 <=；③ 插入本方盘后要保持价格排序（buy 降序 / sell 升序），可用 sort.Slice 或插入到正确位置；④ 金额减法用 Add/Sub，不是 -。

func (h *Handler) getBook(c *gin.Context) {
    // 通过 Book 的只读快照拿盘口（不直接碰 bids/asks 字段）
    bids, asks := h.book.Snapshot()
    c.JSON(200, gin.H{"bids": bids, "asks": asks})
}

func RegisterRoutes(r gin.IRouter, b *Book) {
    h := NewHandler(b)
    r.POST("/orders", h.submitOrder)
    r.GET("/orderbook", h.getBook)
}
注意：handler 不直接操作 bids/asks 字段（它们是 Book 内部状态）——写只经 Submit，读只经 Snapshot。这就是「封装」：别处无法绕过撮合逻辑直接改盘口，读到的也是持锁拷贝而非内部切片。

④ 跑通校验

# 1) 先下一笔卖单（挂卖价 100，量 1）
curl -X POST localhost:8080/orders -H 'Content-Type: application/json' \
  -d '{"user_id":"seller","side":"sell","price":"100","amount":"1"}'
# → trades: []，说明挂进了 asks（没对手盘）

# 2) 再下一笔买单（买价 100，量 1）→ 应该和上面的卖单成交
curl -X POST localhost:8080/orders -H 'Content-Type: application/json' \
  -d '{"user_id":"buyer","side":"buy","price":"100","amount":"1"}'
# → trades: [{ buyer_id:buyer, seller_id:seller, price:"100", amount:"1" }]
#   此时 GET /orderbook 应为空（两边都吃完了）

# 3) 部分成交：卖单量 2，买单量 1 → 成交 1，卖单还剩 1 挂在 asks
curl -X POST localhost:8080/orders -H 'Content-Type: application/json' \
  -d '{"user_id":"s1","side":"sell","price":"100","amount":"2"}'
curl -X POST localhost:8080/orders -H 'Content-Type: application/json' \
  -d '{"user_id":"b1","side":"buy","price":"100","amount":"1"}'
# → 第 2 笔 trades 量=1；GET /orderbook 的 asks 里应还剩 1
校验标准：第 2 步产生一条成交记录、盘口清空；第 3 步产生部分成交、盘口剩 1。两者都满足，本课通过。金额都是字符串（"100"、"1"）——和账户模块的 decimal 序列化一致，后续接账本能直接对上。

⑤ 生产 reality（⚠️ 可选扩展，不转移主线）

主题生产中真实做法你现在
数据结构盘口用红黑树 / 跳表 / 堆，求极值 O(1)、插入 O(log n)切片 + 排序，小盘口够用
撮合精度价格/数量 tick size 约束、整数化（用最小单位整数算）decimal 直接算
持久化盘口快照 + 成交流水落库 / Kafka，崩了可恢复纯内存，重启即丢
成交 → 结算Trade 推给账务服务，原子扣买方钱、加卖方钱只产 Trade，不扣钱
风控前置下单前校验余额/持仓/限购（C 阶段讲）引擎不校验资金
性能单簿单写锁 → 分区/无锁队列/批量撮合一把 sync.Mutex
认知红线：交易所出过的最严重事故，多半是「边界混乱」——把资金校验、限频、风控塞进撮合，导致逻辑互相污染、出 bug 时无法定位。本课刻意让引擎「又聋又哑」只管价格交叉，正是为了把边界立住。后续每一层（账户、风控、对账）都是它的「外部协作者」。
